# dsh-starrail 功能可行性与方案评估

> 目标：先复现现有星铁机器人已具备的功能，再加入模型辅助。
> 本文件只做**评估与选型**，不写实现步骤。所有“已验证”结论都来自本轮真实请求，附实测证据。

---

## 一、外部约束（先划边界，所有方案都在框内比较）

| 约束 | 内容 | 影响 |
|---|---|---|
| 运行形态 | roost 外部 Python 插件，stdin/stdout NDJSON | 无法访问内核内部 API，只能用协议 + 面板 HTTP |
| 主动推送 | 收到 `handled` 后 pending 释放，事后 push 全丢 | 一律「拉取式」：用户发命令查结果 |
| 被动回复额度 | 群聊 5 分钟 / 5 次，单聊 60 分钟 / 4 次（错误码 40034128） | 一条命令只能回一次，多卡片必须合并成一条富媒体 |
| AI 工具注册 | `subprocess.js` 只警告不生效 | DeepSeek 只能由插件直连 API，不能挂成 bot 工具 |
| 数据目录 | 由 roost 下发 dataDir | 所有缓存/库必须在 `data/bots/<bot>/plugins/dsh-starrail/` 下 |
| 开源许可 | 项目 MIT | 引用的第三方数据表必须同为宽松许可并注明出处 |

**本轮修正的关键认知**：旧结论「插件发不了本地图片」**是错的**。实测面板接口 `/api/qq/call` 可以把本地生成的 PNG 以 base64 直传 QQ 并拿到 `file_info`，再用 `sendC2C/sendGroup` 以 `msg_type=7` 发出。详见第四节「图片通道实测」。

## 二、对标对象（现有星铁机器人到底怎么做的）

| 项目 | 生态 | 许可 | 绑定方式 | 数据来源 | 渲染方式 |
|---|---|---|---|---|---|
| `TsukinaKasumi/StarRail-plugin` | 云崽 Yunzai | Apache-2.0 | **手动粘贴 Cookie**（`#cookie帮助`）；扫码只用来重绑 stoken | 米游社 record 接口（ck 直连）+ 三方面板服务（avocado/lulu/sr.roki）兜底 | HTML 模板 + puppeteer 截图 |
| `Ljzd-PRO/nonebot-plugin-mystool` | NoneBot2 | MIT | 账号密码 / 短信登录拿 Cookie；支持游戏 token 扫码 | 便笺走 `hkrpg/aapi/widget`，Cookie 带 stoken + cookie_token | 无图或简单图 |
| `miao-plugin` | 云崽 | MIT | 手动 ck | 米游社 + 本地面板缓存 | HTML 渲染 |
| `mihomo.me` | 第三方服务 | 服务，非代码 | **只要 UID，不要任何凭证** | 自己抓官方公开数据后二次整理 | 其站内自行渲染 |
| `FufuLauncher` / `MHY_Scanner` | 桌面登录器 | MIT | 游戏扫码 → game_token → stoken | 不查数据，只负责登录 | 无 |

**结论**：聊天机器人这一层，**没有一个是靠扫码查数据的**。扫码在生态里只有两个正当用途：拿 `stoken`（抽卡 authkey、月历），以及给登录器用。

`StarRail-plugin` 的能力面（我们要复现的清单）：体力便笺、角色面板（含遗器主副词条、行迹、光锥、遗器评分）、伤害计算、跃迁记录分析、开拓月历、忘却之庭/虚构叙事、模拟宇宙、材料计算、抽卡导出。其代码结构值得借鉴：`runtime/MysSRApi.js`（请求层）、`utils/panel/relicScore.js`（遗器评分）、`utils/damage/`（伤害引擎 + 角色/技能/光锥/套装数据表）。

## 三、逐模块方案评估

### 模块 1：账号绑定

| 方案 | 做法 | 拿到的凭证 | 实测状态 | 风险 |
|---|---|---|---|---|
| A 手动 Cookie | 用户从浏览器复制整行 Cookie | `ltoken_v2` / `ltmid_v2` / `ltuid_v2` / `account_id` / `cookie_token` | 代码已有，**未实测** | 用户操作门槛；Cookie 是敏感信息 |
| B 网页扫码 | passport createQRLogin | 仅 v2 凭证（10 字段，**无 cookie_token、无 stoken**） | ✅ 已跑通，绑定成功 | 后续 record 接口 10041 |
| C 游戏扫码 | combo/panda → game_token → stoken | stoken + ltoken + cookie_token | 取码成功，确认阶段 `-3503` | 需关闭通行证「新设备验证」 |
| D 只绑 UID | 不碰任何凭证 | 无 | ✅ 天然可用 | 只能做面板类功能 |

**优选**：**D 做默认底座 + A 做进阶 + C 只服务抽卡**。
理由：面板/练度走 mihomo 完全不需要凭证（第四节实测），所以「不绑凭证也能用」是这个插件相对同类产品的最大差异化优势；体力、月历这类必须凭证的，用 A（最稳，且能拿到 `cookie_token`）；C 只在用户要抽卡自动化时才需要。

### 模块 2：体力 / 便笺

| 方案 | 端点 | 依赖 | 状态 |
|---|---|---|---|
| A 官方 note | `hkrpg/api/note` | 完整 Cookie | 真 Cookie 返回 **10041** |
| B widget | `hkrpg/aapi/widget` | 完整 Cookie（mystool 同款） | 真 Cookie 返回 **10001** |
| C 首页 index | `hkrpg/api/index` | 完整 Cookie | **10041** |

**结论**：这是**整个项目唯一没有旁路的模块**——体力是实时数据，只能打官方接口。
**优选**：先按 A 走 `#星铁绑定ck`（浏览器 Cookie 含 `cookie_token`），实测 10041 是否消失；若仍 10041，再试 B 的 widget 端点做对照。
**风险等级**：高。建议把该模块排在最后实现，避免它阻塞整体进度。

### 模块 3：练度查询（角色列表 / 详情 / 技能 / 光锥 / 遗器）

| 方案 | 数据源 | 依赖 | 实测 |
|---|---|---|---|
| **A mihomo.me 解析接口** | `GET api.mihomo.me/sr_info_parsed/{uid}?lang=chs` | **只要 UID** | ✅ 200，172KB，`player` + `characters` 全字段 |
| B 官方 index + srCharacterDetail | 米游社 | 完整 Cookie | 受 10041 制约 |
| C 三方面板服务 | avocado / lulu / sr.roki | 无 | StarRail-plugin 已在用，但服务稳定性不可控 |

A 实测字段（以 UID 100041113 为例）：

- `player`：uid / nickname / level / world_level / signature / space_info（均衡等级、角色数、光锥数、遗器数、成就数）
- `characters[]`：`name` `rarity` `rank`（命座）`level` `promotion` `path` `element` `skills` `skill_trees` `light_cone` `relics` `relic_sets` `statistics` `attributes` `additions` `properties`
- `relics[]`：`main_affix`（单条）+ `sub_affix[]`（每条带 `field` / `value` / `display`）+ `set_name` / `rarity` / `level`
- `light_cone`：`name` `rarity` `rank`（叠影）`level` `attributes` `properties`

**限制**：只能拿到用户在米游社「角色展示」里放出来的角色（本次实测账号 129 个角色只解析出 8 个）。这必须在帮助文案里写清楚。
**优选**：**A**。零凭证、零设备风险、字段够全，直接把 10041 绕开。

### 模块 4：遗器词条 → 面板评分 → 伤害预期

分三档，建议**分档落地**，不要一步到位：

| 档位 | 产出 | 实现方式 | 工作量 | 维护成本 |
|---|---|---|---|---|
| L1 词条量化 | 每件遗器主词条 + 4 条副词条的数值、有效词条数、单件评分、套装匹配度 | 自研权重表（按角色定位/元素给副词条权重），纯本地计算 | 中（1~2 天） | 低，新遗器只需补套装匹配 |
| L2 面板总评 | 生命/攻击/防御/速度/暴击率/暴击伤害/元素增伤 汇总，与「达标线」对比 | 同上 + 各属性基准表 | 中 | 中 |
| L3 期望伤害 | 单次技能期望伤害、循环 DPS | 需角色倍率表 + 技能表 + 光锥表 + 套装效果表（`StarRail-plugin` 的 `utils/damage/` 就是这套，Apache-2.0 可复用但要注明） | 大（1~2 周，且需持续跟新角色） | 高 |

**优选**：**L1 + L2 本期落地，L3 作为可选插件化能力延后**，并在 L1/L2 之上叠加 DeepSeek 定性点评（“这套遗器差在哪、该换什么”）。这样“练度要到遗器词条与伤害预期”的诉求在**词条层**得到满足，而数值伤害引擎不成为长期负担。
若后续确实要 L3，先只做 2~3 个热门角色做验证闭环，再决定是否全量移植。

### 模块 5：抽卡分析

| 方案 | 做法 | 依赖 | 备注 |
|---|---|---|---|
| **A 用户粘贴抽卡链接** | 从米游社 App「抽卡记录」复制 URL，取 `authkey` + `uid` | 无 Cookie | UIGF 生态标准做法，authkey 有效期约 24h |
| B 扫码拿 stoken 自动生成 authkey | stoken → authkey | 游戏扫码（`-3503`） | 体验更好，但受设备风控制约 |

数据链路：`getGachaLog` 分页拉全量 → 落 `gacha_record` 表（增量去重）→ 保底/概率统计（角色池 90 抽硬保底、光锥池 80、50-50 判定）→ 导出 UIGF / SRGF JSON。

**优选**：**A 起步**（不依赖任何风控环节，立刻能跑），B 作为后续增强。
**风险**：authkey 会过期，需要明确提示“链接失效请重新复制”。

### 模块 6：图片出图

两个独立问题：**怎么画**、**怎么发**。

#### 6.1 怎么发（本轮实测打通，推翻旧结论）

| 方案 | 机制 | 实测结果 | 结论 |
|---|---|---|---|
| 公网图床 + `image` 字段 | 渲染后上传图床，插件 reply 里给 URL | 只有它这一条时可行 | 依赖第三方，不稳 |
| **面板接口直传** | `POST /api/qq/call` → `uploadMedia`（`fileData` base64）→ `file_info` → `sendC2C/sendGroup`（`msg_type=7`） | ✅ 上传实测 200，返回 `file_uuid` + `file_info` | **首选，零图床依赖** |
| 图床兜底 | `h.uguu.se`（实测可用，3 小时）；catbox / litterbox / tmpfiles 在本网络不可用 | 部分可用 | 备用 |

实测证据：一张 360×140 的测试 PNG（base64 2232 字节）经 `/api/qq/call` 上传，返回
`{"ok":true,"result":{"file_uuid":"...","file_info":"..."}}`。
`api.js` 的 `uploadMedia` 支持 `file_data`（官方上限 5MB，超过走分片），`sendC2C/sendGroup` 透传 `msgType/content/media`，所以整条链路成立。
**注意**：群聊被动回复 5 分钟 5 次的限制依然存在，图文必须合成一条。

#### 6.2 怎么画

| 方案 | 依赖 | 表现力 | 打包体积 | 备注 |
|---|---|---|---|---|
| A Pillow 本地绘制 | 纯 Python（Pillow） | 中（可做总览卡、练度卡，圆角/渐变要做好需手工） | 小 | 无需浏览器，插件秒启动 |
| B HTML 渲染 + Playwright | 需下载 Chromium | 高（可 1:1 复刻现有卡片） | 大（100MB+） | 首次安装慢，roost 的 autoInstallDeps 未必装得下 |
| C 三方渲染服务 | 无 | 高 | 无 | 服务不可控，且要传敏感数据到第三方 |

**优选**：**A 起步**（本机不装浏览器，开箱即用），渲染后端留一个 `render_backend` 配置位，后续可挂 B。

### 模块 7：DeepSeek 接入

| 方案 | 可行性 | 说明 |
|---|---|---|
| 注册成 bot 的 AI 工具 | ❌ | 外部插件不支持，只能由内核插件做 |
| 插件直连 DeepSeek API | ✅ | 配置里放 key；把结构化面板数据（mihomo JSON 精简版）塞进 prompt |
| 走 dsh-roost 现有 AI 能力 | 待查 | 若 roost 有对外 AI 端点可复用，能省一份 key 成本 |

**优选**：插件直连 API + 本地缓存点评结果（同一 UID 24h 内不重复生成）。
产出形态：`#星铁诊断` 返回文本结论（不打分不装权威），或作为练度卡片的附加段落。
**成本控制**：单用户每日次数上限 + 全群每日上限，超出时提示“今日额度用完”。

## 五、选定方案

| 模块 | 选定 | 关键依据 |
|---|---|---|
| 绑定 | UID 免凭证默认；Cookie 手动绑定为进阶；游戏扫码只服务抽卡 | 面板免凭证可跑通，扫码受设备风控 |
| 练度 | mihomo.me `sr_info_parsed` + 本地 SQLite 缓存 | 实测零凭证可用，字段完整 |
| 遗器词条 | L1 词条量化 + L2 面板总评（本地算法） | 工期可控，无需维护倍率大表 |
| 伤害预期 | L3 延后，先只对热门角色做小范围验证 | 避免长期维护负担 |
| 抽卡 | 用户粘贴 authkey，全量拉取 + 增量 + UIGF 导出 | 不依赖任何风控环节 |
| 体力 | Cookie 直连官方 note，待 `10041` 验证 | 唯一无旁路模块，风险最高，排最后 |
| 图片 | Pillow 绘制 + `/api/qq/call` base64 直传 | 零图床、零浏览器依赖 |
| AI | 插件直连 DeepSeek + 结果缓存 + 额度控制 | 外部插件无法注册 AI 工具 |

### 实施顺序（建议）

1. **图片通道**（先做，因为后面每个模块都要出图，是公共基础设施）
2. **练度查询**（免凭证、可立刻见效，验证 mihomo 稳定性）
3. **遗器词条 + 面板评分**（练度的深化）
4. **抽卡分析**（独立链路，authkey）
5. **DeepSeek 点评**（叠加在 2/3 之上）
6. **体力 / 月历**（依赖 Cookie 打通，放最后攻坚）

## 六、风险与未验证项

| 项 | 状态 | 应对 |
|---|---|---|
| `10041` 是否可由浏览器 Cookie 解决 | **未验证**，需用户配合 | 若不行，降级为「体力模块暂缓」，其余模块不受影响 |
| 米游社「新设备验证」是否可关 | 需用户操作 | 关掉后游戏扫码可复活，仅作为抽卡自动化增强 |
| mihomo.me 第三方稳定性/限流 | 未知 | 本地缓存 + 失败提示 + 可配置备用源 |
| 群聊被动回复 5 分钟 5 次 | 已确认 | 一条命令一条富媒体消息，禁止拆成多发 |
| 遗器/角色数据表版权 | StarRail-plugin 为 Apache-2.0 | 若复用须在 README 与文件头注明来源与许可 |
| 第三方数据表跟新角色滞后 | 长期问题 | L1/L2 用权重表，不硬编码角色倍率，降耦合 |
